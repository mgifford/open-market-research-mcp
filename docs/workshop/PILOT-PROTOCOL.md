# Workshop pilot protocol

Use this protocol to run and document a real pilot. Until a pilot is complete,
the repository must describe the materials as **untested**.

## Purpose

Learn whether the fictional exercise helps learners distinguish user needs,
market alternatives, ACR claims, missing evidence, and agency decision points.
The pilot is not a procurement evaluation and does not test a real product.

## Participants

- Recruit acquisition professionals and, separately or together, people with
  disabilities who use the web.
- Offer participation in the mode the person prefers: in person, remote,
  asynchronous, keyboard-only, screen reader, magnification, or speech input.
- Compensate participation time where policy allows.
- Do not require disclosure of a disability or a medical diagnosis.

## Consent and data

- Explain the purpose, time, recording, and how notes will be used.
- Obtain explicit consent before recording audio, video, or screen activity.
- Use only the fictional fixture. Do not ask for real acquisition records.
- Store notes on an approved system; do not commit participant data to the
  repository or paste it into an external AI service.
- Offer a way to withdraw and delete notes.

## Session outline

1. Welcome, consent, and access check (5 minutes).
2. Complete the scope and alternatives sections with the app (20 minutes).
3. Ask the participant to find one ACR-related gap and explain what they would
   request next (10 minutes).
4. Ask them to export and critique the report (10 minutes).
5. Debrief and feedback (10 minutes).

## What to observe

- Where the participant hesitates or asks for help.
- Whether the source catalogue and labels are understandable.
- Whether “missing,” “not evaluated,” and “does not support” are distinguished.
- Whether the participant can operate the full flow by keyboard and with their
  assistive technology.
- Whether the report is understandable without the facilitator explaining it.
- Any moment where the interface implies a ranking, approval, or conformance
  conclusion.

## Measures

Use descriptive evidence, not a single score:

- task completion and assistance required;
- time on each section;
- errors and recovery;
- quotes or paraphrases with consent;
- accessibility barriers with the technology and version used;
- facilitator observations separated from participant statements.

Do not report a success rate without the number of participants, tasks, and
assistance conditions.

## After the pilot

- Write a short report with participants, methods, access accommodations,
  findings, limitations, and changes made.
- Separate participant evidence from facilitator interpretation.
- File accessibility barriers with reproduction steps and the environment.
- Update the worksheet and report only where the evidence supports it.
- Re-run the affected tasks after changes.
- Add the pilot report to this directory using
  [PILOT-REPORT-TEMPLATE.md](PILOT-REPORT-TEMPLATE.md) and remove the
  “untested” status only when the report exists.

## Stop conditions

Stop or pause the session if a participant is distressed, if real sensitive
data is about to be entered, if a recording was not consented to, or if an
accessibility barrier prevents participation and cannot be worked around.
